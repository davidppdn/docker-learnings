[2] - First Dockerfile
Today, I have learned several interesting things about docker, by creating a dockerfile.
* First, I learned that docker images are prepackaged environments that can be run on any machine with docker installed.
* Images are immutable templates and containers are instances of those images. You can have multiple containers from the same image, each with its own isolated env.
* I learned that while docker containers use the same resources, they are isolated from the host machine and other containers, so its fresh.
* Because of the above, I learned that you need to copy the files you need into the docker image, and not rely on the host machine's file system.
* Because of the above, I also learned that each command you run creates a new layer in docker, where each subsequent layer needs to be de-cached.
  Thus, there is an optimal order to run commands in a dockerfile, such as copying and building dependencies first, then the code, because
  dependencies are less likely to change than code, and thus can be cached more often.
* I also learned about multi stage builds, where you can have a build stage that compiles your code, and then a final stage that copies the compiled code into a smaller image, which is more efficient.
  This is because for deployment, you dont need stuff like the whole sdk, just the runtime. 
* Next, docker context is the set of files that are available to the docker daemon when building an image. This is important because copy paths are relative to the context.
* Finally, you dont need to copy everything, because folders like bin and obj are auto generated. Saves speed!

--name: assigns a name to the container, so you can refer to it by name instead of id

[4] - Docker volumes
Learned about the lifecycle difference between containers and volumees. 
Files inside contains get destroyed when the container is destroyed.
A volume is storage separate from the container, stored either on the host machine or in a specific
location manager by docker. Volumes are persistent, and can be shared between containers. 
When a container is destroyed, the volume remains, and can be reattached to a new container.

[5] - Creating a volume and attaching it to a container
To create a volume, use the command: docker volume create <volume_name>
To inspect a volume, use the command: docker volume inspect <volume_name>
The inspect command will give you several details about the volume, including its mount point on the host machine.
The mount point is the location on the host machine where the volumnes data is stored.
To mount the volumne to a container, use the following:
docker run -v <volume_name>:<container_path> <image_name>
the container_path is inside the container where the volume is accessible. Thus, anything
written to <container_path> will be written to the volume, and thus persist even if the container is destroyed.

[6] - Running Postgres in a container
docker run -d `
  --name taskmanager-db `
  -e POSTGRES_USER=taskmanager `
  -e POSTGRES_PASSWORD=devpassword `
  -e POSTGRES_DB=taskmanager `
  -v taskmanager-postgres:/var/lib/postgresql `
  -p 5432:5432 `
  postgres:18

  -e set the environment variables needed for the postgres container to run
  we expose port 5432, which is the default port for postgres, so we can connect to it from the host machine
  --name is the name of the container, so we can refer to it by name instead of id
  -d runs in detach mode, so it runs in the background instead of attaching to a terminal

We connect to it by running:
docker exec -it taskmanager-db psql -U taskmanager -d taskmanager
  -it runs the command in interactive mode, so we can interact with the container
  psql is the postgres command line tool, which we use to connect to the database
  -U specifies the user to connect as, which is taskmanager
  -d specifies the database to connect to, which is also taskmanager

[7] - Docker networks
Since docker containers run on their own environments, localhost is not the hosts localhost, but the containers.
Because of that, there needs to be some network configuration to allow containers to talk to each other.
That is what a docker network is for.

docker network create <network_name>
docker network connect <network_name> <container_name>
docker run -d --name <container_name> --network <network_name> -p <host_port>:<container_port> <image_name>
docker network inspect <network_name>

When joining a network, docker autoassigns ip addresses to the containers. Because of this,
it is better that we let docker auto assign the network ip addresses and use container names.
This is because the ip addresses can change when containers are restarted, but the names will remain the same.

[8] - The tech discussion
I learned about two interesting... libraries? Npgsql and EF core.
Npgsql is a .NET data provider for postgres, that allows .NET applications to connect to postgres databases. 
It is a low level library that provides a way to execute SQL commands and retrieve results.
EF core is an object relational mapper (ORM) that allows .NET applications to interact with databases using 
objects instead of SQL commands. The two belong to different layers of absteraction, and are usually
used in tandem. For the sake of the project, and for learning a bit of sql as well, I will only use
Npgsql for now.

[9] - Connection pooling
This is unrelated but interesting nonetheless, so I am writing it down. 
A connection pool is a cache of database connections that can be reused, 
instead of creating a new connection every time one is needed. When a connection is requested, 
the pool will return an available connection from the pool. When the connection is done, instead
of closing it, it is returned to the pool fo rreuse. The benefits of this is that it 
reduces the overhead of creating and destroying connections, which can be expensive,
while also improving performance by reducing the time it takes to establish a connection.
Additionally, it also means that there isnt constant connection between the application and the database, 
which can be a security risk.

[10] - Docker build
Small intervention to the note. 
docker build -t <image_name> <path_to_dockerfile> 
is a command that builds a docker image from a dockerfile. 
The -t flag tags the image with a name, and the path is the location of the dockerfile.
When you update the dockerfile, or even the code, you need to rebuild the image, and then run a new container from the new image.
Because the image contains the application code, and the container is an instance of the image, 
the container will not update when the image is updated.
